MM2 Auto-Delivery Architecture

Website/API → Delivery Queue → Windows Roblox Worker → Trade Verification → Order Updated. External Windows automation and vision control the Roblox client — no injected executor.

Inside the Windows Roblox Worker one per bot account

Each worker is an independent process controlling one Roblox client through external Windows automation and screen vision — no injected executor. Workers report to the API and never talk to each other.

Inventory is tracked per bot, so the queue only assigns orders a bot can actually fulfill. A missed heartbeat flags the worker as down and its order is requeued.

When a Trade Fails

Each rung runs only if the previous one didn't recover the order. Every step is logged against the order.

1 · retryRetry the tradeSame bot retries with a delay, up to the retry limit.
2 · requeueRequeue the orderOrder returns to the queue for a later attempt.
3 · restartRestart Roblox clientWorker relaunches a stuck or crashed client.
4 · reassignAssign another botA different bot with the item in stock takes the order.
5 · alertAlert the adminOrder flagged for manual review and resolution.

What Changes When Roblox Updates

The client-control layer is the only part coupled to Roblox/MM2 UI. When the game changes, that layer is re-tuned; everything else keeps running untouched.
